# Internationalization and Localization

A reference for evaluating code from an internationalization (i18n) / localization (l10n) lens during review. Used by the `i18n` subagent. The scope is **the contract failures that ship when "it works in English / it works in my timezone / it works for ASCII names."**

Distinct from `accessibility` (UI semantics for users with disabilities), `readability` (code-as-prose for developers), `documentation` (doc quality at API boundaries), and `security` (though there is overlap: Trojan Source attacks, IDN homograph attacks, BiDi controls in user-controlled text).

The core thesis: most i18n bugs are **implicit assumptions baked into single-language single-locale single-timezone testing**. The agent's lens is to catch these assumptions before they reach a user whose language, locale, calendar, or script breaks them.

The operational thesis: **the world is more various than your test data.** Plural rules vary (Polish has four categories; Arabic six), name structures vary (mononyms, two-surname systems, family-name-first cultures), date formats vary (MDY / DMY / YMD), week starts vary (Sunday / Monday / Saturday), zero-decimal currencies exist (JPY), three-decimal currencies exist (KWD, JOD), case folding is locale-aware (Turkish `i` / `İ`), filesystem normalization varies (macOS HFS+ NFD, others NFC), and source code itself can be lied about (Trojan Source 2021).

## Universal principles

### Unicode is the text model; bytes / code units / code points / grapheme clusters are four different lengths

Every modern text question has the same first sub-question: "in what unit?"

- **Bytes**: raw memory. UTF-8 uses 1-4 bytes per code point.
- **Code units**: the encoding's atomic chunk. UTF-8: 1 byte. UTF-16: 2 bytes (surrogate pairs for astral code points).
- **Code points**: Unicode scalar values (U+0000 through U+10FFFF). One Unicode "character" in the abstract sense, but many user-perceived characters are multiple code points.
- **Grapheme clusters**: user-perceived characters. "é" can be one code point (U+00E9, precomposed) or two (U+0065 U+0301, decomposed); both render as one grapheme. Emoji families (👨‍👩‍👧‍👦) are 7+ code points joined with ZWJ but one grapheme.

**Flag**: `name.length`, `name[0]`, `name.slice(0, N)`, `name.substring`, `name.startsWith` -- ask "in what unit?" In Swift, `String.count` is grapheme clusters (correct default). In JS, `string.length` is UTF-16 code units (often wrong for user-facing length); use `Intl.Segmenter` or `[...string].length` for code points, `Intl.Segmenter` for graphemes. In Python 3, `len(s)` is code points. In Go, `len(s)` is bytes; `utf8.RuneCountInString` is code points; grapheme clusters need `unicode/norm` + manual segmentation. In Rust, `s.len()` is bytes; `.chars().count()` is code points; `unicode-segmentation` crate for graphemes.

### Normalization: NFC, NFD, NFKC, NFKD

Unicode has multiple representations for visually-identical text. "é" can be precomposed (NFC: U+00E9) or decomposed (NFD: U+0065 + U+0301). Strings that look the same can compare unequal byte-wise.

- **NFC** (Composition): preferred for web, JSON, most output.
- **NFD** (Decomposition): macOS HFS+ filesystem normalization.
- **NFKC / NFKD** (Compatibility): also folds compatibility variants (full-width Latin → half-width). Use carefully -- lossy.

**Flag**: identifier comparison without normalization (usernames, emails, file paths); password storage without normalization (a user types `é` precomposed, then later decomposed -- login fails); cross-platform sync that doesn't normalize at the boundary (macOS NFD ↔ Linux/Windows NFC); URL handling without UTS #46 / IDNA 2008.

### Locale-aware vs invariant comparison

Case folding is locale-aware. Turkish `i.toUpperCase()` returns `İ` (U+0130, dotted capital I), not `I`. `"admin".toUpperCase() == "ADMIN"` is `false` in Turkish locale. German `ß.toUpperCase()` historically returned `SS`; Unicode 5.1 added `ẞ` (capital sharp s).

**Flag**: case-insensitive identifier comparison using locale-aware operations (`.toUpperCase()`, `.toLowerCase()`); use `String.Equals(StringComparison.OrdinalIgnoreCase)` in .NET, `equalsIgnoreCase` in Java (still has issues; prefer ICU), `s.to_ascii_lowercase()` in Rust for ASCII-only identifiers, explicit invariant culture. **Never compare case-insensitively across locales without explicit locale specification.**

### Avoid string concatenation for human-readable text

Word order varies. English: "John added Alice to the team." German: "John fügte Alice zum Team hinzu." Hungarian: family name first; Japanese: subject often elided. Any template with `"Welcome " + name + "!"` cannot be translated correctly.

**Flag**: any user-facing string assembled by concatenation, interpolation, or templating without going through a translation system. Always use a message-format library (ICU MessageFormat, Fluent, gettext, framework's localization API). Never concatenate; always parameterize.

### Pluralization is six categories, not two

CLDR defines six plural categories: **zero, one, two, few, many, other**. English uses two (one, other). Polish uses four (one, few, many, other). Russian uses three (one, few, many) with complex rules (`22 books` is `few`, `12 books` is `many`, `21 books` is `one`). Arabic uses six. Welsh uses six.

**Flag**: `${count} item${count === 1 ? '' : 's'}` style logic. Always use ICU MessageFormat `{count, plural, one {# item} other {# items}}` or equivalent. The library handles per-locale rules.

**Flag**: pluralization tests that only cover n=0, n=1, n=many. Need n=2 (Welsh), n=12 (Polish: 12 ends in 2 but is "many"), n=22 (Russian: `few` because last digit 2, but n=12 is `many`).

## Text encoding

### UTF-8 by default, everywhere

UTF-8 is the de facto standard. JEP 400 (JDK 18, 2022) finally made it Java's default for I/O. JavaScript files default to UTF-8. Python 3 source is UTF-8 by default. Modern Linux is UTF-8 everywhere. Windows is the holdout but PowerShell 7+ and modern Windows 10/11 console default to UTF-8.

**Flag**: any explicit encoding choice other than UTF-8 without a documented reason; `Charset.defaultCharset()` (use `StandardCharsets.UTF_8`); `string.encode('ascii')` (loses non-ASCII data); MySQL `utf8` charset (limited to BMP; use `utf8mb4`); BOM in UTF-8 files (causes parsing issues in many tools).

### Mojibake

The garbage when bytes are decoded as the wrong encoding. UTF-8 read as Latin-1: "é" becomes "Ã©". UTF-8 read as Windows-1252: similar. The fingerprint is `Ã` followed by punctuation-shaped characters, or `â€™` for `'`.

**Flag**: code that re-encodes (`s.encode('latin-1').decode('utf-8')`); double-encoding paths; database columns whose stored bytes have a different encoding than the connection declared.

### The `Atomics.wait` / SharedArrayBuffer escape hatch in browsers

Out of scope for i18n review; route to `concurrency`.

## Pluralization, gender, agreement

### ICU MessageFormat is the standard

```
{count, plural,
  =0 {No items}
  one {# item}
  few {# items}
  many {# items}
  other {# items}
}
```

Mozilla Fluent is a more recent alternative with better DX. Gettext's `ngettext(singular, plural, n)` is the historical default but cannot represent six categories.

**Flag**: `ngettext` calls in code that ships to languages requiring more than two forms; concatenated translations; pluralization logic in application code instead of in the message format.

### Gender / select

Many languages have grammatical gender that affects translation. ICU's `select`:

```
{gender, select,
  female {She added you to her team}
  male {He added you to his team}
  other {They added you to their team}
}
```

**Flag**: translations that assume gender (pronouns, adjective endings) without a select mechanism; UI that asks for binary gender to drive translation (use neutral / non-binary forms where possible, or let users pick pronouns directly).

### Lists

"A, B, and C" in English; "A, B et C" in French; "A、B、Cおよび" in Japanese.

**Flag**: list joining with hardcoded separators. Use `Intl.ListFormat` (JS), `ListFormatter` (Swift), `MessageFormat` list patterns.

## Dates, times, calendars

### Always use IANA tz database names

`America/New_York`, not `EST` (ambiguous: Eastern Standard Time or Australian Eastern Standard Time). `Asia/Tokyo`, not `JST`. The tz database (Olson) is updated several times per year as governments change DST rules; ship code that consults the system, not a snapshot.

**Flag**: 3-letter timezone abbreviations in stored data; hardcoded UTC offsets in user-facing scheduling (DST will break them); `pytz` in modern Python (use `zoneinfo`, PEP 615, Python 3.9+); stale timezone data baked into a Docker image with no update path.

### "Store UTC" is not a silver bullet (John Skeet)

For instants in the past, UTC is correct. For instants in the future scheduled in a specific locale, storing UTC is **wrong** -- if the timezone's DST rules change between now and then (governments do change rules), the UTC-converted time becomes incorrect.

The pattern: store `(local_datetime, tz_name)` for future scheduled events; convert to UTC at the moment of execution. The Noda Time / Java `java.time.ZonedDateTime` model is correct.

**Flag**: future calendar events stored as UTC instants; meeting times that drift after a DST rule change in the host country.

### Naive datetime is a bug

Any `datetime` / `Date` / timestamp without a timezone is ambiguous and lossy.

**Flag**: Python `datetime.datetime` without `tzinfo`; JavaScript `Date` arithmetic across DST boundaries (use Temporal proposal where available, or Luxon / date-fns-tz); Java `java.util.Date` (no timezone; use `java.time.*`); SQL `TIMESTAMP WITHOUT TIME ZONE` (use `TIMESTAMP WITH TIME ZONE` or `TIMESTAMPTZ`).

### DST transitions: skipped and repeated times

When clocks spring forward, some local times don't exist (e.g., `2:30 AM` on the spring-forward date). When clocks fall back, some local times occur twice. API behavior varies: throws, picks one, ambiguous.

**Flag**: scheduled jobs at "2 AM local time" without DST consideration; time-based access controls in server's timezone; alarms / reminders that don't survive DST transitions.

### Calendar systems

CLDR supports Gregorian, Hebrew, Islamic (Hijri), Persian (Solar Hijri), Buddhist, Japanese imperial, Chinese, Indian national, and more. The Hijri calendar's start of day varies (sunset, not midnight). Japanese imperial calendar has era boundaries (Reiwa began 2019-05-01, mid-day).

**Flag**: apps targeting non-Gregorian audiences without calendar selection; assumption that "year, month, day" maps to Gregorian.

### Date format ordering

MDY (US), DMY (UK, much of Europe, India, Africa), YMD (ISO 8601, much of Asia). `01/02/2024` is January 2 in the US, February 1 in the UK.

**Flag**: hardcoded date format strings (`yyyy-MM-dd` is fine for machine-readable; `MM/dd/yyyy` is wrong for user display anywhere outside the US); `Date.parse` on user input (engine-dependent); display dates not going through `Intl.DateTimeFormat` / `DateFormatter` / `DateTimeFormatter`.

### Week start

Sunday (US, Israel, parts of Asia); Monday (ISO 8601, Europe, much of the world); Saturday (much of the Middle East). Calendar widgets must respect locale.

### Y2K38

UNIX signed 32-bit `time_t` overflows at 2038-01-19 03:14:07 UTC. 64-bit `time_t` is standard on modern Linux/BSD; embedded systems and some legacy code aren't.

**Flag**: 32-bit signed integers used for Unix timestamps; database columns sized for 32-bit Unix time on systems that will live past 2038.

## Numbers, currency, units

### Decimal and group separators

`1,234.56` (US, UK, Asia mostly) vs `1.234,56` (continental Europe) vs `1 234,56` (France, SI standard) vs `1'234.56` (Switzerland).

Indian numbering uses lakhs and crores: `12,34,567` instead of `1,234,567`.

**Flag**: hardcoded `,` thousands separator or `.` decimal in user-facing numbers; `parseFloat("1,5")` on user input (returns 1 in en-US locale); display through `Intl.NumberFormat`.

### Currency

ISO 4217 currency codes (`USD`, `EUR`, `JPY`, `KWD`). Positioning varies: `$100`, `100€`, `100 €`, `R$100,00`. Decimal places vary: JPY 0, USD/EUR 2, KWD/JOD/BHD 3.

**Flag**: hardcoded `$` or `€` or 2 decimal places; `(amount / 100).toFixed(2)` patterns (wrong for JPY and KWD); use `Intl.NumberFormat(locale, { style: 'currency', currency: 'JPY' })`.

### Storage

Money should be stored as **minor units integer + currency code**: `{amount: 1099, currency: "USD"}` for $10.99. Never floating-point. Display formatting separate from storage.

**Flag**: money as `float` / `double`; money without a currency code; money operations that assume 2 decimal places.

## Sorting and collation

ASCII byte sort is wrong for any language with non-ASCII letters. German `ä, ö, ü` sort with their unaccented forms (DIN 5007-1) or after `z` in Swedish. Spanish `ñ` was historically a separate letter after `n`. Estonian sorts `Z` between `S` and `T`. Turkish `ı` (dotless i) and `i` are distinct letters.

UTS #10 (Unicode Collation Algorithm) and the DUCET (Default Unicode Collation Element Table) are the foundation. `Intl.Collator` / `java.text.Collator` / `Collator` (Swift) use them.

**Flag**: `ORDER BY` on user-facing names without locale-aware collation; sort that doesn't go through `Intl.Collator` / framework equivalent; database `COLLATE` clauses missing in `ORDER BY` on text columns; `.sort()` of names in JS without comparator.

## URLs, IDN, identifiers

### Internationalized Domain Names (IDN)

Punycode encodes non-ASCII domain names: `münchen.de` is `xn--mnchen-3ya.de` on the wire. IDNA 2008 (RFC 5891) standardized the conversion; UTS #46 added compatibility processing.

**Flag**: URL parsing that doesn't go through a IDN-aware library; IDN homograph attacks (Cyrillic `а` looks like Latin `a` -- `wikipediа.org` with Cyrillic `а` is registerable); rendering URLs to users without IDN warning UI (browsers handle this; CLI tools often don't).

### Internationalized email (EAI)

RFC 6532 allows non-ASCII in local parts and domains. SMTP support varies; many MTAs still strip non-ASCII.

**Flag**: email validation regex that excludes non-ASCII; SMTP code without SMTPUTF8 negotiation when targeting international users.

### Language tags (BCP 47)

`en`, `en-US`, `en-Latn-US`, `zh-Hant-TW`, `sr-Cyrl`, `de-1996`. `Accept-Language` HTTP header lists user preferences with quality factors.

**Flag**: language tags with underscores instead of hyphens (`en_US` -- common but technically wrong); locale matching that doesn't honor fallback chains (`en-AU` should fall back to `en` if `en-AU` not available); hardcoded two-letter codes when script disambiguation matters (`zh` could be Hans or Hant).

## Filesystems, paths, identifiers

### Filesystem normalization

macOS HFS+ stores filenames in NFD; APFS preserves what's written; Linux ext4/btrfs preserve bytes; Windows NTFS uses UTF-16. Cross-platform sync is a minefield.

**Flag**: filenames compared without normalization across OS boundaries; ZIP / TAR archives created on one platform unpacking with broken filenames on another.

### Path separators

Windows: `\`. Unix: `/`. Modern Windows accepts both for file APIs. URL and most cross-platform tools use `/`.

**Flag**: hardcoded `/` or `\` in paths; use `path.join` / `pathlib.Path()` / `std::path::Path`.

### Case-sensitive vs case-insensitive filesystems

macOS HFS+ defaults to case-insensitive; Linux is case-sensitive; Windows is case-insensitive. "Foo.txt" and "foo.txt" may or may not be the same file.

**Flag**: code that creates files differing only by case (works on Linux, conflicts on macOS / Windows); case-insensitive comparison that uses locale-aware folding instead of ASCII or Unicode-case-fold.

## Right-to-left (RTL) and bidirectional text

### Bidi (BiDi) basics

UAX #9 (Unicode Bidirectional Algorithm). RTL languages: Arabic, Hebrew, Persian, Urdu, Yiddish, N'ko. Mixed-direction text (e.g., English phone number in Arabic UI) has a logical order and a visual order; the algorithm maps between them.

**Flag**: text concatenation across direction boundaries without explicit isolation (`⁨`...`⁩` First-Strong Isolate, or HTML `<bdi>`); user-controlled text in titles / labels / IDs without `<bdi>` wrapping (a Hebrew username breaks LTR sentence flow).

### RTL UI mirroring

The UI mirrors in RTL: navigation flows right-to-left, breadcrumbs reverse, sliders flip, scrollbars move. Icons mostly mirror (arrows yes, mailboxes no, clocks contested).

**Flag**: hardcoded `margin-left` / `padding-right` / `left:` CSS (use logical properties `margin-inline-start`, `padding-inline-end`, `inset-inline-start`); fixed icon directions without `dir`-aware variants; layouts tested in LTR only.

### Trojan Source (CVE-2021-42574, 2021)

Boucher & Anderson (Cambridge) showed that BiDi control characters (U+202A through U+202E) in source code can make the visual order differ from the logical order. A code reviewer sees one program; the compiler executes another.

**Flag**: source code containing unexpected BiDi controls (CI should detect; many languages added warnings post-2021); user-controlled strings included in logs / source without sanitization.

## Names, addresses, phone numbers

### Names

Patrick McKenzie's "Falsehoods Programmers Believe About Names" (2010) -- the canonical reference. Forty assumptions that don't hold:

- People do not always have a first/last name structure.
- People do not always have exactly one canonical name.
- Names can change.
- Names include apostrophes, hyphens, spaces, accents.
- Names can be a single mononym.
- Family name can precede given name (Chinese, Japanese, Korean, Hungarian, Vietnamese).
- Spanish-speakers often have two surnames (paternal + maternal).
- Names are not always representable in ASCII.

**Flag**: separate `first_name` / `last_name` columns enforced as required; name validation that rejects apostrophes, hyphens, spaces, non-ASCII; templates that hardcode `${user.firstName} ${user.lastName}` order; assumption that `lastName` is the family name (in Hungarian / Chinese / Japanese, family name comes first by tradition); use `PersonNameFormatter` (ICU 72+) or store a single `display_name` and let users format it.

### Addresses

Format varies wildly. Japan: postal code, prefecture, city, ward, block, building. China: country, province, city, district, street. UK: alphanumeric postcode. Buildings have no street numbers in some areas.

**Flag**: required state/province field for users outside US/CA; numeric-only postal codes; address concatenation in code (use locale-aware address formatters or just display lines in user-supplied order).

### Phone numbers

Use Google's libphonenumber (or ports). Country codes, variable lengths, internal formatting differ.

**Flag**: phone validation by regex; assumption of fixed length; assumption of digits-only.

## Input methods (IME) and entry

### East Asian IMEs

Chinese / Japanese / Korean text entry uses composition: the user types a sequence of keys; the IME assembles into the desired script; composition is committed on selection. Events: `compositionstart`, `compositionupdate`, `compositionend`.

**Flag**: `onChange` / `oninput` handlers that fire during composition without checking composition state -- typing in CJK IME breaks; React-specific: controlled inputs with `onChange` calling `setState` during composition cause flicker. Listen for `compositionstart` / `compositionend` to gate.

## Text expansion / contraction

German text averages ~30% longer than English; Chinese ~50% shorter; Arabic varies. Buttons and labels designed for English clip or wrap in other languages.

**Flag**: fixed-width buttons, fixed-height containers, text that must fit a specific pixel size; use flexible layouts (CSS flexbox / grid with `min-content`); pseudo-locale testing in CI catches this systematically (Mozilla's pseudo, Microsoft's pseudo).

### Truncation

Cutting mid-grapheme produces invalid sequences. Cutting mid-emoji-ZWJ-sequence produces broken emoji. Cutting mid-combining-sequence breaks accented characters.

**Flag**: `s.substring(0, N)` / `s[:N]` on user-facing text without grapheme awareness; use `Intl.Segmenter` (JS), `unicode-segmentation` (Rust), `BreakIterator` (Java/Swift); for line-breaking use UAX #14 (`@line-break`, `\b`-aware iterators).

## Translation workflow

### Key conventions

Common patterns: hierarchical (`home.button.signin`), flat (`Home_Button_SignIn`), or source-text (`Sign In`). Each has tradeoffs.

**Flag**: missing-key handling that silently returns the key instead of falling back to source language or warning; keys built dynamically (`t(\`button.${name}\`)`); -- impossible to extract statically); duplicate keys across files.

### Translation memory

CAT tools (Crowdin, Lokalise, Phrase, Transifex) provide TM, MT pre-fill, and human review. The agent should check that the project has a workflow, not just hardcoded strings.

### HTML and component substitution in translations

Translators occasionally inject `<script>` tags. The library should escape on render by default; component-substitution (FormatJS `<link>...</link>` style) is the safest pattern.

**Flag**: `dangerouslySetInnerHTML` with translated strings; HTML strings in translation files without sanitization; concatenating translations with `+` and HTML.

## Anti-pattern catalog

The signal-to-noise list:

- **Hardcoded English strings in source.** `<button>Submit</button>` instead of `<button>{t('form.submit')}</button>`.
- **String concatenation for translations.** `"Welcome " + name + "!"`.
- **`name.length` / `name[0]` on user-facing text.** Pick the right unit.
- **Locale-dependent comparisons in tests.** Tests passing in en-US but failing in tr-TR.
- **Date math on naive Date.** `new Date(now.getTime() + 24*60*60*1000)` across DST.
- **Storing local time without timezone.** `"2024-03-10 14:30:00"` -- which timezone?
- **Hardcoded date / number / currency formats.** `MM/dd/yyyy`, `$${n.toFixed(2)}`.
- **Address concatenation in code.** `street + ", " + city + ", " + state + " " + zip`.
- **Phone regex.** Use libphonenumber.
- **Email regex that excludes non-ASCII.** Use minimal regex + verification email.
- **"Last name" / "first name" universal name structure.** Many cultures don't divide this way.
- **`${user.firstName} ${user.lastName}` in templates.** Name order varies.
- **Currency hardcoding `$` or 2 decimal places.**
- **Byte-order sort for user-facing lists.** Use `Intl.Collator`.
- **Hardcoded path separators.** Use `path.join` / `pathlib.Path` / `std::path::Path`.
- **Truncation without grapheme awareness.** Cuts emoji in half.
- **`Date.parse` on user input.** Engine-dependent (locale-dependent).
- **`parseFloat` on locale-formatted user input.** `parseFloat("1,5")` is 1 in en-US.
- **Counting lines with `\n` only.** Windows `\r\n`, classic Mac `\r`, Unicode U+2028 / U+2029.
- **Width-assumption layouts.** Fixed-width buttons break in German.
- **Truncating emoji.** Multi-codepoint ZWJ sequences cut wrong.
- **Pseudo-locale not in CI.** Layout / expansion / RTL bugs slip past manual review.
- **Server returning errors in server's locale.** Thread `Accept-Language` through.
- **Validation messages hardcoded in English.** Configure `joi` / `zod` / `class-validator` for translation.
- **HTML in translation strings without sanitization or component substitution.**
- **Time-based access controls in server's timezone.** Document and store with timezone.
- **MySQL `utf8`.** Use `utf8mb4`. Default since 8.0 but legacy databases persist.
- **JavaScript `Date` API for non-trivial date logic.** Use Temporal proposal (Stage 3) or Luxon / date-fns-tz / Day.js.
- **`os.system` / `subprocess` with locale-dependent output parsing.** Set `LC_ALL=C` or use machine-readable output flags.
- **Assuming `<html lang>` equals user preference.** The document language is the document's language, not the user's preference.

## What is NOT an i18n finding

Signal-to-noise:

- **Internal-only tools / dev infrastructure** where English-only is the explicit design.
- **Generated bindings, lock files, fixtures, build scripts.**
- **Hardcoded strings in test fixtures and example code** (unless they document a behavior the agent's lens cares about, like Turkish I).
- **Style choices the team has deliberately made** (e.g., not localizing error codes, only error messages).
- **Currency / date / time hardcoded in code that intentionally serves only one locale** (a US-only SaaS may legitimately hardcode `$` and `MM/dd/yyyy` -- but the README should say so).
- **Performance concerns around locale-aware operations.** Route to `performance`.
- **Security concerns about BiDi controls, IDN homographs.** Mention; route to `security`.
- **Accessibility concerns about RTL screen-reader behavior.** Route to `accessibility`.

## Severity calibration

Using `panel-contract.md`'s rubric; specific calibration:

- **blocker**: data loss from encoding mismatch (MySQL `utf8` storing emoji); timezone bugs in scheduled future events (DST rule change → wrong meeting time); name validation that rejects valid international names (excludes real users); naive date arithmetic across DST in a critical path; sort that produces visibly wrong order for a supported locale.
- **major**: hardcoded English strings in user-facing UI; missing pluralization (English-only `count + ' items'`); `Date.parse` / `parseFloat` on user input; truncation without grapheme awareness on user-facing display; non-IANA timezone names in stored data; address concatenation; phone regex; missing `Accept-Language` plumbing.
- **minor**: missing pseudo-locale in CI; missing CSS logical properties; missing IME composition handling on inputs; non-NFC normalization at storage boundary.
- **nit**: language tag with underscore instead of hyphen; minor inconsistency in date format strings; BOM in UTF-8 file.
- **insight**: structural -- "this app has accreted three i18n libraries; consider standardizing"; "consider adopting ICU MessageFormat for plurals throughout."

Confidence: high when the trigger is concrete (a specific call site, a specific locale that breaks it); medium when reasoned (a class of layouts that probably break in German, but the agent hasn't tested).

## Process for the i18n agent

1. **Identify the surface.** Is this user-facing UI, server-side processing, data storage, file handling, or all of the above?
2. **Read project i18n conventions.** `docs/i18n.md`, sections in `CLAUDE.md`, the translation directory layout (`locales/`, `i18n/`, `messages/`), the chosen library (i18next, FormatJS, react-intl, vue-i18n, gettext, Fluent), lint rules.
3. **Walk the bug-shape catalog** for each region: text encoding / normalization, pluralization, gender, lists, dates / times / timezones, numbers / currency, sorting, URLs / IDN, file paths, RTL / BiDi, names / addresses / phones, IME / composition, text expansion / truncation.
4. **For each user-facing string**, ask: "is this going through translation?" If hardcoded, flag.
5. **For each date / time operation**, ask: "what timezone, what calendar, what format?"
6. **For each numeric formatting site**, ask: "what locale, what currency, what unit?"
7. **For each text manipulation** (length, substring, split, sort, compare), ask: "in what unit, in what locale, with what normalization?"
8. **For each storage boundary**, ask: "what encoding, what normalization, what timezone metadata?"
9. **Route to other lenses**: encoding security (BiDi, IDN homographs) → `security`; RTL screen-reader behavior → `accessibility`; locale-aware operation cost → `performance`.
10. **Stay read-only.**
